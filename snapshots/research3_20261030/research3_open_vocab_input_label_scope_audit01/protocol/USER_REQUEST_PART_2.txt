### 7.3 父子技术映射核验

对涉及父技术与子技术的案例，实际追踪：

`author label → original technique ID → parent ID → subtechnique ID → frozen candidate ID → frozen definition`

每一步都要记录原始字段、转换规则、来源路径和版本。

核查以下风险：

- 父技术 ID 与子技术 ID 混用；
- 技术名称相同但 ID 不同；
- 子技术被错误归并到父技术；
- Gold 在父技术层级，而候选定义在子技术层级；
- 父技术正文不包含当前子技术所需的具体行为条件；
- 技术名称、战术字段或变体标题被误当作行为正文；
- 不同 ATT&CK 版本的定义或映射规则混用；
- 标签转换过程丢失原始技术 ID。

只有存在实际字段或来源证据时，才能将某个问题认定为映射错误。

## 八、第五阶段：追溯知识提取、转换和渲染链

本阶段必须实际检查已有代码和转换记录，不仅比较最终文本。

### 8.1 追溯数据处理链

针对 12 个竞争技术和 34 条范围疑问，建立：

`原始知识来源 → 原始字段 → 提取脚本 → 中间数据 → 映射规则 → 文本转换 → 冻结知识文档 → 候选评价`

每个环节记录：

- 文件路径；
- 文件哈希；
- 代码或提交版本；
- 相关字段；
- 具体转换操作；
- 输入与输出字段；
- 是否存在缺失；
- 是否能够从现有材料复现；
- 证据强度。

若某个中间环节缺失，不得根据最终文本反推并声称已确认其处理过程。

### 8.2 文本长度与截断审计

对 12 个技术的冻结文本，记录：

- 原始字节数；
- 原始字符数；
- 冻结文本字节数；
- 冻结文本字符数；
- 字段级长度；
- 是否存在固定长度截断规则；
- 是否存在标题拼接；
- 是否存在描述字段被过滤；
- 是否存在字符编码或序列化异常。

如果原始来源不存在，就不能通过比较文本长度认定发生了截断。

如果冻结文本长度恰好达到某个阈值，只能将其作为检查线索，不能直接判定 `TEXT_TRUNCATION_CONFIRMED`。

### 8.3 代码核验

仅静态检查已有提取、转换和映射代码，确认：

- 是否实际读取了描述字段；
- 是否使用了正确的字段名；
- 是否把变体标题拼接到描述字段；
- 是否在序列化前截断文本；
- 是否过滤了空字段；
- 是否发生 ID 覆盖或错误去重；
- 是否使用了不匹配的父子技术映射；
- 是否在候选生成过程中改变了技术粒度。

如果必须执行已有代码才能验证某项行为，应先检查其副作用和读取范围。

本轮默认只允许静态代码审计和已有回执核验。任何需要重新提取大数据、重新生成候选知识或写入历史目录的操作均不执行。

### 8.4 缺陷证据等级

每个问题必须标记以下证据等级之一：

- `LEVEL_1_DIRECT_SOURCE_PROOF`：原始来源与冻结输出可直接对照；
- `LEVEL_2_REPRODUCIBLE_TRANSFORMATION_PROOF`：已有代码及输入输出能够复现具体转换问题；
- `LEVEL_3_INDIRECT_ARTIFACT_EVIDENCE`：存在间接迹象，但缺少完整来源链；
- `LEVEL_4_UNVERIFIED_HYPOTHESIS`：只有待核验的推测。

只有前两级可以用于确认具体的数据处理缺陷，并且必须说明确认范围。

即使缺陷已经确认，也不能直接认定该缺陷导致了模型漏召回。预测因果影响属于另一个需要公平实验才能回答的问题。
